# Dlight 渐进优化设计

日期：2026-08-23
状态：核心里程碑已交付
路线：稳定性 → 用户体验 → 架构治理

## 1. 背景

Dlight 已具备首页、动漫库、搜索、播放、弹幕、评论、用户中心、历史、收藏和离线下载等完整功能。当前主要问题不是功能不足，而是同一能力存在多套实现和配置，导致网络环境、第三方资源或依赖发生变化时，问题容易跨模块扩散。

现状中的高风险点包括：

- API 地址分散在 `Param`、`ApiConfig` 等位置，并包含模拟器、局域网和线上地址。
- 图片同时使用 Glide 和 Picasso，不同加载器使用不同网络与证书策略。
- 多个 `OkHttpClient` 独立创建，超时、证书、代理和日志策略不一致。
- Material、OkHttp、Glide 等依赖存在重复版本，且 AndroidX 与旧 Support Library 混用。
- 发布签名密码写在 Gradle 文件中，应用全局允许明文流量并申请部分高风险权限。
- 播放器、下载和评论相关类职责较多，核心逻辑难以脱离 Android UI 测试。
- 主要业务流程缺少实际自动化测试保护。

本设计采用渐进式加固，不进行整仓重写。每个阶段必须独立可构建、可运行、可验收，并以当前阶段通过为进入下一阶段的门禁。

## 2. 产品目标

### 2.1 用户目标

- 首页、搜索、详情和播放在正常网络下可稳定完成主流程。
- 网络、图片或播放源失败时，用户能理解原因并执行重试或换源。
- 下载状态真实、可恢复，失败后不丢失任务上下文。
- 历史、收藏和播放进度在重启后保持一致。

### 2.2 工程目标

- 同类能力只有一个权威配置入口和一套默认实现。
- 播放源选择、下载状态、URL 处理等核心规则可以在 JVM 测试中验证。
- Activity 和 Fragment 不再持有可独立测试的网络、下载或数据同步规则。
- 每次提交能够自动执行构建、测试和必要的静态检查。

### 2.3 非目标

本轮路线不包含：

- 迁移到 Kotlin 或 Jetpack Compose。
- 更换 GSYVideoPlayer 或整体重写播放器。
- 引入依赖注入框架。
- 重做后端业务或增加新的内容来源。
- 为追求形式统一而一次性迁移所有页面到 MVVM。

## 3. 实施原则

1. 先保护主流程，再改变内部结构。
2. 一次只迁移一种职责，避免同时更改网络、UI 和数据模型。
3. 新旧实现短暂并存时必须有明确迁移边界和删除条件。
4. 不以“构建成功”代替运行验证；网络、图片、播放和下载必须分别取证。
5. 不删除无关示例或历史代码，除非已证明没有入口和引用。

## 4. 阶段一：稳定性基线

### 4.1 网络配置统一

建立单一运行时网络配置入口，取代业务代码中的硬编码地址。

- Debug 默认保留模拟器宿主机地址，允许通过构建参数覆盖。
- Release 只允许使用显式配置的 HTTPS 地址；未配置时构建失败，不静默回退到测试环境。
- API 地址规范化为带结尾 `/` 的合法 URL。
- `Param` 仅保留与设备环境相关的职责，API 地址不再由多个类分别维护。

### 4.2 网络客户端分层

网络策略按用途分为三类：

- API Client：访问自有后端，负责认证、JSON、统一超时与结构化错误。
- Image Client：访问第三方图片，使用系统证书、缓存、占位图和失败重试。
- Media Client：访问视频与 m3u8，保留播放器所需的重定向、Range 和来源切换能力。

三类客户端共享公共连接配置，但不得让图片代理或第三方证书策略影响本地 API。禁止使用恒为特定 IP 判断的 `hostnameVerifier`。

### 4.3 图片加载统一

- 统一使用 Glide，移除 Picasso 依赖和调用。
- 所有列表图片必须定义 placeholder、error 和裁剪策略。
- View 回收时由 Glide 生命周期自动取消旧请求。
- 头像、本地封面和第三方封面使用同一入口，但允许按用途配置变换。

### 4.4 依赖与权限治理

- 每个依赖只保留一个版本来源。
- 移除旧 `com.android.support` 依赖，全部使用 AndroidX。
- 签名密码改为环境变量或未提交的本地属性。
- 将明文流量许可收敛到 Debug 或必要域名，不在 Release 全局开启。
- 删除经引用检查确认不需要的 `WRITE_SETTINGS`、`SYSTEM_ALERT_WINDOW` 和旧存储权限。

### 4.5 错误处理

定义统一错误类别：网络不可用、超时、服务器错误、解析错误、资源失效、存储不足和未知错误。UI 使用用户可理解的文本，不直接显示异常堆栈。

所有主要请求至少具备：

- 明确的 loading/content/empty/error 状态。
- 手动重试入口。
- 防止重复请求的状态约束。
- 调试构建中的必要日志，不记录 token、密码或完整用户数据。

### 4.6 测试基线

优先增加以下 JVM 测试：

- API 地址规范化和环境选择。
- 图片与本地 URL 的改写规则。
- HLS 播放源筛选和备用源顺序。
- m3u8 相对地址解析。
- 下载状态转换、暂停、恢复和失败重试。
- 下载任务序列化与恢复。

增加最小 Android 冒烟测试：启动 App、加载首页、打开详情、进入播放器。

### 4.7 阶段一验收

- `./gradlew assembleDebug` 成功。
- 阶段一新增测试全部通过。
- 模拟器在本地 API 环境下可加载首页数据和第三方封面。
- 搜索、详情和至少一个播放源可用。
- 下载暂停后可恢复，重启 App 后任务状态不丢失。
- 断网或接口失败时 App 不崩溃，并显示可重试状态。
- 仓库不包含明文签名密码。

## 5. 阶段二：用户体验

### 5.1 页面状态

首页、动漫库、搜索、详情、历史、收藏和下载页统一支持：

- 首次加载骨架屏。
- 加载成功内容态。
- 无内容空状态。
- 离线或服务失败状态。
- 用户主动重试。

### 5.2 首页与列表

- 标题最多显示两行，卡片尺寸和间距在不同屏宽下保持一致。
- 列表图片使用统一比例，加载成功后轻量渐入。
- 周更筛选保留当前选择和缓存，刷新时不闪回默认项。
- 数据刷新不清空仍可展示的旧内容。

### 5.3 播放体验

- 播放失败区分网络错误与资源失效。
- 当前源失败时允许重试或切换备用源。
- 记录集数和播放进度，在首页、详情和历史中提供继续播放。
- 自动恢复播放必须提示恢复位置，并允许从头播放。

### 5.4 下载体验

- 展示进度、速度、预计剩余时间和任务状态。
- 失败任务展示原因和重试按钮。
- 移动网络开始大文件下载前请求确认。
- 存储不足时在创建任务前阻止下载并提示所需空间。
- 已完成任务能够校验文件存在性，文件丢失时不显示为可播放。

### 5.5 无障碍与适配

- 关键图片和按钮提供 content description。
- 触摸目标不小于 Android 推荐尺寸。
- 支持系统字体放大，主要操作不被裁切。
- 检查暗色背景上的文字与按钮对比度。

### 5.6 阶段二验收

- 主要页面均具备 loading/content/empty/error 四态。
- 播放失败不退出页面即可重试或切换线路。
- 继续播放能够恢复到正确集数和近似进度。
- 下载页面准确展示状态，失败任务可重试。
- 大字体和 TalkBack 下主流程仍可操作。

## 6. 阶段三：架构治理

### 6.1 渐进式边界

以改动频率和风险排序迁移：

1. 下载模块。
2. 播放源与播放进度模块。
3. 首页与搜索数据加载。
4. 评论和用户同步。

每次迁移只处理一个模块，不创建全局 BaseActivity、万能 Repository 或无明确消费者的抽象。

### 6.2 目标职责

- Activity/Fragment：保留界面、导航和少量请求编排。
- Tracker/Policy：页面请求 generation、分页、恢复和预检状态。
- Data Source/Engine：具体网络、数据库、下载、HLS 和播放器能力。
- ViewModel/Repository：仅在后续新增复杂页面时按需引入，不作为本里程碑的全量迁移要求。

核心状态使用明确的数据类型表达，避免以多个 boolean 推断任务状态。

### 6.3 大类拆分

优先从 `DanmkuVideoActivity` 和下载相关类中提取：

- 播放源解析与选择。
- 播放进度记录。
- 弹幕请求与发送。
- 下载命令和状态转换。
- UI 状态映射。

提取必须由测试保护，不进行与目标职责无关的格式化或重命名。

### 6.4 CI 与质量门禁

CI 至少执行：

- Debug 构建。
- JVM 单元测试。
- Android Lint。
- 敏感信息和重复依赖的基础检查。

发布流程在后续独立设计中处理，本阶段不自动发布 APK。

### 6.5 阶段三验收

- 下载和播放源核心规则可脱离 Android UI 测试。
- 播放源、HLS、下载文件、网络安全、Room 迁移和页面请求状态已从 Activity/Fragment 中提取为可测试单元。
- 新功能遵循明确的数据流边界。
- CI 在新提交上稳定执行构建、测试和 lint。
- 重构前后的用户主流程行为一致。

## 7. 数据流

```text
用户操作
  → Activity / Fragment
  → Tracker / Policy
  → Retrofit API / Room / Download Engine / Media Engine
  → 结构化结果或错误
  → 页面状态
  → UI 渲染
```

现有页面继续使用 XML/ViewBinding，并将高风险状态与规则逐项提取到可测试的 Tracker/Policy/Engine。后续只有在页面复杂度需要时才引入 ViewModel/Repository，避免为了架构形式一次性重写稳定页面。

## 8. 回滚与兼容策略

- 每个阶段拆成小提交，网络、图片、依赖和权限不混在同一提交中。
- 替换图片库时按页面迁移，页面验证通过后再删除 Picasso。
- 新下载状态需要兼容当前 SharedPreferences 中的旧任务数据。
- Room schema 若发生变化必须提供 Migration，不使用破坏性重建。
- 无法确认线上 API 或证书配置时，Release 网络配置不做猜测性修改。

## 9. 交付顺序

1. 阶段一实施计划与风险检查。
2. 阶段一实现、测试、模拟器验证和提交。
3. 阶段一验收记录。
4. 阶段二实施计划、实现和验收。
5. 阶段三按模块分别计划、实现和验收。

下一阶段只能在上一阶段的验收证据完整后开始。

## 10. 里程碑收口决策

本节覆盖前文中与当前里程碑范围冲突的表述。

### 10.1 已交付

- 单一 API 环境与客户端策略；API base URL 仅允许 origin 根路径。
- Glide-only 图片加载、URL 解析、占位/失败策略和头像缓存失效。
- 平台 TLS、Release HTTPS/cleartext 策略、签名环境变量和权限收敛。
- 播放源选择、恢复匹配、播放器错误/全屏错误重试。
- HLS 安全解析、重定向与 DNS pin、原子分片、指纹续传和进程中断协调。
- 下载速度、ETA、计费网络确认、离线与低存储预检。
- Room v1→v2 显式迁移、legacy 稳定快照合并和 structured source 持久化。
- 首页、动漫库、搜索的 loading/content/empty/error/retry 与请求竞态控制。
- 可访问状态组件、评论 BottomSheet 短屏/IME 适配、app lint 0-error 门禁。
- 单一 Retrofit 扩展路径、维护文档同步和 Debug/Release 自动化测试。

### 10.2 从当前里程碑移出的项目

- 骨架屏动画：当前使用无额外依赖、支持 TalkBack 的明确 loading 状态；视觉骨架动画属于后续设计优化。
- 精确毫秒播放位置恢复：当前保留集数级恢复；时间点恢复需要单独定义播放器回调频率、Room v3 schema 和隐私/同步语义。
- 全量 MVVM/Repository 迁移：当前采用按风险提取的 Tracker/Policy/Engine，不为形式统一重写稳定页面。
- 自动发布 APK：CI 仅构建、测试、lint 和安全扫描；发布及签名托管另行设计。

### 10.3 仍需人工设备验收

- 真实 CDN 播放、全屏错误恢复及代理/DNS 组合。
- 下载暂停、系统杀进程、恢复、计费网络与低存储场景。
- Room legacy 真机升级、评论输入法/分屏、大字体和 TalkBack 完整路径。

这些项目不阻塞代码里程碑交付，但在正式对外发布前必须完成设备验收记录。
